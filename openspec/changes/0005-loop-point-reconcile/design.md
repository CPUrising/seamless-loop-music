# Design: 循环点校正策略

## 决策

### D1：以解码器为唯一真值

- 扫描期为了性能使用 TagLib 读头（`CreateTrackFromFile`），播放期必须打开解码器。
- 对扩展名与容器不符、或 TagLib 解析异常的文件，两者会不一致。播放行为只能由解码器决定，因此校正**只在加载时**进行。

### D2：只修正"整曲循环"与越界值

| 情形 | 处理 | 理由 |
|---|---|---|
| `LoopEnd <= 0` 或 `LoopEnd >= 库中 TotalSamples` | 设为真实总数 | 这是扫描写入的默认值，语义就是"整曲" |
| `LoopEnd > 真实总数` | 收敛到真实总数 | 不收敛会立刻触发循环跳转 |
| `LoopStart >= 真实总数` 或 `< 0` | 归零 | 越界起点无意义 |
| 其余（用户设过的小区间循环） | 保持不变 | 避免破坏用户的循环设置 |

### D3：校正结果写回数据库

- 否则每次加载都重复校正，且 UI 其他入口（列表、详情）仍显示错误时长。
- 复用既有 `ITrackRepository.UpdateLoopPoints`，不新增 schema。

### D4：不动扫描期元数据来源

- 若扫描期改用解码器，需要为每个文件打开解码器（M4A 走 Media Foundation），会明显拉长扫描时间，且不属于本次 bug 的必需修复。
- 因此扫描仍用 TagLib，播放时自愈。

## 风险

| 风险 | 缓解 |
|---|---|
| 用户刻意把 `LoopEnd` 设为整曲（等于旧总数） | 语义上与"整曲"一致，校正后仍是整曲，只是长度正确 |
| 校正写库失败 | `UpdateLoopPoints` 已有既有实现；异常会冒泡到 `LoadTrackAsync` 的调用方，与现状一致 |
| 总数差异仅由解码器四舍五入导致 | 使用 1000 采样容差，避免抖动 |
